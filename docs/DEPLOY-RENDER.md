# Render deployment and data preservation

## Recommended bundled deployment

The root render.yaml provisions one paid Starter web service and a 1 GB persistent disk at /var/data. React and Express share one domain, avoiding separate API URL/CORS mistakes. Render's normal filesystem is ephemeral; the persistent disk is essential for this SQLite configuration. Do not switch to a free web service with local SQLite.

1. Create a private GitHub repository and upload the project source. Exclude backend/data, all .env files, node_modules and frontend/dist. The ZIP retains your original database locally; Git ignores it intentionally.
2. In Render choose New > Blueprint, connect that repository and select render.yaml. Review current plan/disk charges before creating resources.
3. Enter RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET and RAZORPAY_WEBHOOK_SECRET, initially using test keys. JWT_SECRET is generated by the blueprint. Do not regenerate it on every deploy.
4. Deploy. Build: `npm ci --prefix backend && npm ci --prefix frontend && npm run build --prefix frontend`. Start: `cd backend && npm start`. Health: `/api/health`.
5. Confirm Disk mount /var/data and SQLITE_PATH=/var/data/architect_connect.sqlite. The application refuses Render SQLite paths outside /var/data, but you must still verify that a real disk is attached.
6. New production installations start with an empty database. In Render Shell, enter backend if necessary. Temporarily set ADMIN_EMAIL and ADMIN_PASSWORD (12+ characters), run `npm run create-admin`, then remove these bootstrap variables.
7. Register client/designer accounts normally. To add the public trial dataset deliberately, run `ALLOW_DEMO_SEED=true npm run seed` in Render Shell. This creates a public demo administrator: do this only for a trial site.
8. Set the Razorpay webhook URL to `https://YOUR-SERVICE.onrender.com/api/payments/webhook`, subscribe to payment.captured and order.paid, and use the matching webhook secret. Enable automatic capture in Razorpay. Test callback, cancellation, capture and browser-close recovery before switching to live keys.

## Import your existing database without overwriting anything

The original ZIP database is NOT imported automatically into production. This prevents accidental exposure of demo credentials and overwriting a live database.

1. Locally, stop the server and run `npm run backup` in backend. Use the generated backup, not a raw copy of an actively written SQLite/WAL file.
2. Upload that backup through Render SSH/SFTP into `/var/data/import-source.sqlite`. Copy the exact service SSH/SFTP command from Render's dashboard.
3. In Render Shell, from backend, run:

```bash
SQLITE_PATH=/var/data/imported.sqlite npm run import:sqlite -- /var/data/import-source.sqlite
```

This refuses to overwrite an existing destination. Keep the active destination untouched while importing. Then change the service SQLITE_PATH to `/var/data/imported.sqlite` and redeploy. Startup applies additive missing-column migrations. Keep the previous database until you have verified counts, login, inquiries and fees. Before switching to imported demo data, replace all public demo passwords.

## Persistence acceptance test

Create a unique client and inquiry, send a message, record their IDs. Restart the service, then redeploy the same repository. Log back in and verify both records and messages remain. Check that the database file and backups reside on the mounted disk. Never run sync({force:true}), destructive resets or seed commands that drop tables.

Automatic backups are stored next to the database in backups/. Download them off Render daily; a backup on the same disk does not cover disk/account loss. Restore by importing a backup to a new filename and switching SQLITE_PATH as above. Test restores periodically. No system can guarantee zero data loss under every failure.

SQLite disk deployments run a single instance; do not horizontally scale this setup. For larger concurrent workloads, use the existing MySQL configuration with an external persistent MySQL service and its backup/recovery facilities. Switching engines requires an explicit data migration; changing DB_DIALECT alone does not transfer records.

## Payment reconciliation

A payment provider timeout can leave an order in `creating`. It is deliberately blocked from automatic recreation to prevent duplicate payable orders. Search Razorpay by the local payment UUID receipt and reconcile the order ID before retrying. Never reset a payment row without checking the provider. Late captured payments are applied by signed webhooks. Refunds and designer payouts must be handled through your merchant operations; they are outside this implementation.
