# Arch + Connect

A portfolio and project inquiry platform that connects clients with architects and interior designers. Clients can browse professionals, compare fee estimates, explore projects, exchange messages and pay a project's professional design fee through Razorpay.

> This repository contains deployment configuration, not proof of a live deployment. Sample studios, project descriptions and accounts are fictional. Images are illustrative references with credits.

## Features

- Client, designer and administrator accounts with role-based access.
- Designer discovery by name, location, style, experience and rating.
- Professional profiles with separate design-fee and materials-budget estimates.
- Portfolio creation, published project browsing and saved-designer API support.
- Project inquiries, participant-only messaging and controlled project status changes.
- Client reviews for completed projects and administrator analytics.
- Razorpay orders, server-side signature/capture verification, signed webhooks and payment receipts.
- Responsive React interface with 110 distinct bundled demo images.
- Persistent SQLite configuration for Render, consistent backups and safe database import.

## Run locally on Windows

Install Node.js 22.12 or newer and npm. For the commands below, open PowerShell in the project root: the folder containing `backend`, `frontend` and `render.yaml`.

### 1. Start the backend

```powershell
cd backend
npm ci
npm run setup
npm start
```

`npm run setup` creates a local `.env` with a random JWT secret if one does not already exist. Existing environment settings are kept. Leave this terminal running; the API listens on port 5000 by default.

### 2. Start the frontend

Open a second PowerShell window in the project root:

```powershell
cd frontend
npm ci
npm run dev
```

Open **http://localhost:5173**. The development proxy forwards `/api` requests to the backend. Production uses the same origin for the frontend and API.

## Environment settings

Edit `backend/.env`; never commit this file.

```env
PORT=5000
JWT_SECRET=your-random-secret-with-at-least-32-characters
DB_DIALECT=sqlite
SQLITE_PATH=./data/architect_connect.sqlite
AUTO_BACKUP=true
CLIENT_URL=http://localhost:5173
RAZORPAY_KEY_ID=
RAZORPAY_KEY_SECRET=
RAZORPAY_WEBHOOK_SECRET=
```

Keep the random secret generated by setup, or replace it with your own securely generated value. `CLIENT_URL` is useful for a separate frontend origin. The bundled Render deployment does not require a separate frontend URL. Leave `frontend`'s `VITE_API_URL` blank for the development proxy and same-origin deployment.

MySQL settings are documented in `backend/.env.example`. Changing database engines does not transfer existing records; an explicit migration is required. The executed integration tests use SQLite.

### Choose a local database

The usual local path is `./data/architect_connect.sqlite`. The package also provides `./demo/trial.sqlite` with sample inquiry fee/material values. To select that database, change `SQLITE_PATH` in `backend/.env` and restart:

```env
SQLITE_PATH=./demo/trial.sqlite
```

Switching paths selects a different database; it does not merge records. Some historical inquiries in the older database may have zero fee values because the original application discarded those fields. Those historical amounts cannot be reconstructed automatically.

### Add or update sample data

Stop the backend first. Run these commands **inside `backend`** as needed:

| Command | Behavior |
|---|---|
| `npm run seed` | Creates the core sample dataset, then expands it; skips if the existing demo marker is present |
| `npm run demo:expand` | Adds missing sample designer accounts and their projects; existing accounts are skipped |
| `npm run demo:update` | Restores recognized demo profiles/projects from `demo/architects.json`; overwrites their editable sample values |
| `npm run demo:images` | Updates only recognized sample profile/project images |

Expansion, refresh and image-update commands create a SQLite backup first. Sample updates are transactional; repeat expansion does not create duplicate accounts/projects. They do not delete existing inquiries, messages or payments. A production seed/expansion requires an intentional `ALLOW_DEMO_SEED=true` setting.

To edit a real architect's fee, sign in as that designer and use **Dashboard → Minimum/Maximum architect fee → Save profile**. Profile fees are estimates; changing them does not alter existing inquiry fees.

## Razorpay setup

1. Add your Razorpay test key ID, key secret and a separate webhook secret to the backend environment.
2. Configure your public webhook URL as `https://YOUR-DOMAIN/api/payments/webhook`.
3. Subscribe to `payment.captured` and `order.paid`, using the matching webhook secret. Configure automatic capture in Razorpay.
4. Create an inquiry as a client, accept it as its designer, then open it as the client and select **Pay design fee**.

The amount comes from the stored inquiry's professional fee. Materials are separate. Payments are marked paid only after captured-payment details match the stored order, amount and currency. Signed webhooks update records if the browser callback is interrupted.

Test keys simulate payments. Live payments require your activated merchant account, live keys and live webhook configuration. Real gateway transactions have not been verified in this workspace. Funds go to the platform's merchant account; automatic designer payouts, escrow and refunds are not implemented.

Never put secret keys in frontend code. An uncertain provider-order creation may require manual reconciliation before another order can be created; see [the deployment guide](docs/DEPLOY-RENDER.md).

## Deploy on Render

The root `render.yaml` configures a paid Starter web service and a persistent disk. Both frontend and backend use one service.

1. Push the source to a private GitHub repository.
2. In Render, select **New → Blueprint** and connect the repository.
3. Use `render.yaml`, enter your Razorpay environment values and review resource charges before deploying.
4. Verify the following configuration:

| Setting | Value |
|---|---|
| Root directory | Repository root |
| Build | `npm ci --prefix backend && npm ci --prefix frontend && npm run build --prefix frontend` |
| Start | `cd backend && npm start` |
| Health check | `/api/health` |
| Persistent disk mount | `/var/data` |
| `SQLITE_PATH` | `/var/data/architect_connect.sqlite` |
| `AUTO_BACKUP` | `true` |

**Do not deploy this SQLite configuration on an ephemeral filesystem.** Keep the persistent disk attached and the database under its mount path. Do not run database seeding/imports during the build; run them in the service's runtime shell.

For existing-data transfer, production administrator setup, payment configuration and recovery steps, follow [docs/DEPLOY-RENDER.md](docs/DEPLOY-RENDER.md). Keep any changed `SQLITE_PATH` consistent with `render.yaml` so a Blueprint sync does not switch the selected database back.

After deployment, create a record and message, restart the service, redeploy, and verify that both remain. This single-instance disk configuration is not designed for horizontal scaling.

## Backups and data safety

From `backend`:

```powershell
npm run backup
```

SQLite backups use `VACUUM INTO` to create a consistent snapshot. With `AUTO_BACKUP=true`, the server also creates backups at startup and every 24 hours while running. Backups default to a `backups` directory beside the selected database.

- Keep existing `backend/data` and `.env` files when updating application code.
- Do not use destructive resets or `sync({ force: true })` against your database.
- Download backups off the server regularly. A backup on the same disk does not cover loss of that disk.
- Monitor disk usage; backup retention is manual.
- Test restoring a backup to a new database filename before switching the active path.

No setup can promise zero data loss under every failure. The persistent disk addresses routine restart/redeploy persistence; offsite backups and restore checks cover additional failures.
